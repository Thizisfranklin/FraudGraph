# FraudGraph Analyst Workbench — Product Concept (NOT YET DEPLOYED)

## Who is the user?

A financial-crime / risk analyst reviewing suspicious **Bitcoin transaction networks**, not a consumer looking up whether a named person is a criminal. The goal is a **human investigation aid**, not automated accusation, account blocking or legal determination.

## Better product framing

**"FraudGraph Investigator: Why did this transaction enter the review queue, what is its network context, and how reliable is the model in this time period?"**

This is more defensible and useful than an app that promises to say whether an arbitrary Bitcoin wallet or transaction is fraudulent. Elliptic++ has transaction nodes with anonymized IDs and incomplete, selectively known labels. It cannot reliably resolve wallet ownership or score an arbitrary live Bitcoin TXID from only a string.

### Suggested analyst flow

1. **Choose a transaction from the available dataset or an authorized enriched data feed.** Display the transaction's dataset ID, time bucket, feature availability, known/unknown label, and whether enough inputs exist to score. Avoid live lookups until a separately designed, auditable data-ingestion service exists.
2. **Explore its neighborhood.** Show the transaction as a central node and observed predecessor/successor transactions as directed edges; allow one-hop expansion with a strict node cap to avoid clutter. Use interactive zoom, tooltips, edge direction and a legend for known labels vs unknown.
3. **Compare model evidence.** Show rank or score from transaction-only versus graph-enhanced models, their decision-time features, and whether the model has degraded in the relevant period. Scores are **not calibrated probabilities**.
4. **Show why the model prioritized it.** Present feature contributions (with strong caveats about correlation and noncausality), the graph structure, and concrete visible data, not "reason for guilt".
5. **Review workload and tradeoffs.** Allow analysts to choose 1%, 5%, 10% review capacity and see the known-illicit capture, known licit cases and unknowns occupying capacity. Do not report "true fraud recall" when the ground truth is missing.
6. **Record analyst decisions.** A note with timestamp, evidence links, unresolved facts and disposition such as "needs more information", "escalate for review", or "not prioritized". Never mark an unlabeled dataset item as certainly licit.
7. **Export an evidence summary.** Include data provenance, model version, score date, graph snapshot cutoff, important limitations and analyst annotations.

## Research visualizations we can build immediately

The new offline interactive report generated by `scripts/build_research_dashboard.py` already explores:
- training-versus-forward-validation AP by model capacity and strategy;
- sensitivity to hypothetical 2/4/6-bucket label availability;
- review capacity versus captured known illicit transactions;
- input drift and observed change around time step 43;
- opt-in post-hoc replay, clearly labeled as already inspected.

Unlike a product app, this report is **read-only**, does not accept arbitrary wallet identifiers, and does not make live predictions. We should validate it with analysts before building deployment features.

## Suggested MVP architecture (future work)

- **First iteration:** Streamlit or a small React UI, Plotly charts, a NetworkX-backed neighborhood service and filtered **saved** transaction predictions; local or authenticated deployment.
- **After validation:** FastAPI backend, versioned model/scoring service, time-aware feature store, audit logs, permissioned case notes and data quality/monitoring service.
- **Data pipeline:** Versioned source → validated transaction attributes/edges → as-of graph snapshots → frozen model version → score and explanation → analyst queue.
- **Operational monitoring:** Missing/late data, label coverage/maturation, feature drift, score drift, analyst workload, delayed-outcome AP, model version and rollback triggers.

## Essential prerequisites

1. An explicit **prediction-time contract**. Current work assumes batch scoring at the end of each time bucket. Out-degree/PageRank can use same-bucket information **after** an individual transaction, so they are not safe for instantaneous alerting.
2. A **valid input contract**. Arbitrary Bitcoin TXID lookup is impossible from anonymized source IDs alone, and a real blockchain feed would need legal access, schema mapping, graph feature construction and model validation.
3. **Prospective assessment** with genuinely new and representative data, not just the already-inspected steps 40–49.
4. Known label-maturation dates, calibrated scores and a clear human-review policy.
5. Security, privacy, responsible-use controls, access boundaries, retention rules and documented nonautomated disposition.

## Success criteria for the MVP

Analysts can explain why a transaction was ranked, navigate graph context without excessive clutter, distinguish known outcomes from unknowns, and reproduce a case report from pinned source and model versions. Improvement should be measured by analyst time, evidence quality, queue quality and false-escalation burden—not just one AP score.

**Not implemented in this change:** live Bitcoin data lookup, wallet identity inference, transaction scoring API, hosted interface, fraud verdicts or automatic enforcement.
